# Generic deployment guide

1. Install the root and `server` dependencies.
2. Build the web client with `npm run build:h5`.
3. Copy `deploy/server.env.example` to `server/.env` and replace every `CHANGE_ME` value.
4. Use a dedicated MySQL account with only the permissions required by this application.
5. Start `server/index.js` with a process manager and reverse-proxy HTTPS traffic to the application port configured in `server/.env`.
6. Keep `server/.env`, uploaded files, user profiles, database exports and signing certificates outside Git.

The application never creates a default user. To create the first administrator, provide `ADMIN_USERNAME`, `ADMIN_PASSWORD` and optionally `ADMIN_NICKNAME`, then run `npm --prefix server run admin:create`. The password must contain at least 12 characters and occupy at most 72 UTF-8 bytes; it is never written to the repository. Existing bcrypt passwords can still be used for login even when their historical input exceeded 72 bytes.

Production startup fails when `PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` or a sufficiently long `JWT_SECRET` is missing. This is intentional.

## Material storage and previews

Run exactly **one Node application process**. The upload reservations, mutation locks and fair preview queue are process-local. Do not enable cluster mode, multiple replicas, or run the preview backfill CLI concurrently with the application. A deployment needing multiple writers must first move admission/reservations and the preview queue to shared transactional storage.

Material uploads stream to private temporary files. A file may be up to 500MiB; all files in one multipart request may total up to 600MiB. The Nginx example allows 601MiB to include bounded multipart overhead. Each account may have two active uploads, and the process accepts eight in total. Pending quota checks and mutations are also capped at four per account and 32 globally; disconnected checks are skipped before scanning. Reservations remain held until active disk work settles even if the response disconnects. The web client sends at most two staged files concurrently. Excess requests return 429; size/quota errors return 413, and insufficient free disk returns 507. Nginx must overwrite `X-Forwarded-For` with `$remote_addr`; Express trusts only loopback proxies.

Default retained storage limits are 10GiB/account and 100GiB/process, configured by `MATERIAL_ACCOUNT_BYTES` and `MATERIAL_GLOBAL_BYTES`. Originals, generated previews, staged files, extraction output and retained trash all count. Reservations also cover concurrent requests and copies. In-flight files can temporarily be counted both as disk usage and as reserved bytes; leave headroom when setting the limits. There must remain at least `MATERIAL_MIN_FREE_BYTES` (default 1GiB) on every storage and temporary volume after all active reservations. Requests are rejected when existing data is already over budget; existing files are preserved.

There are also finite caps: 20 upload tasks and 200 materials per account (200 tasks/2,000 materials globally), 2,000 retained files per account (20,000 globally), and 200 attachments per task/material. Counts include generated files and trash. Permanent deletion or expiry releases capacity. Staging expires after six hours. Cleanup only deletes a directory with a valid, expired server manifest or incoming-upload lease; unknown legacy directories are counted and preserved for an operator to inspect.

The conversion queue admits at most 64 jobs including the active job and eight per account. Accounts are served in round robin order. If admission fails, the original remains saved and the preview reports a queue-limit message; run `npm --prefix server run previews:backfill` during a maintenance window with the server stopped to rebuild those previews. Backfill now loads published file ownership from the database and waits for queue capacity. Startup resumes previously queued work without blocking HTTP startup. Moving a material to trash, permanently deleting it or removing an attachment cancels pending work, terminates the active converter process group/tree and waits for cleanup before moving/deleting files. Reservations remain held until that work settles; restored or replaced files can start new preview jobs. Each video job has a separate temporary output directory, so older previews do not consume its per-job output limit. Conversion inputs and outputs are capped at 500MiB; default timeouts are 240 seconds for Office and 300 seconds for video. Timeout overrides must be 1,000–1,800,000ms. On Linux `/usr/bin/prlimit` is required: converters inherit a 2GiB address-space limit, a CPU-time limit and a 500MiB per-file output limit. Other supported desktop platforms retain timeout/output checks; use external OS isolation for equivalent hard process memory/CPU limits. Windows process-tree cancellation uses `taskkill /T /F` and must be checked in the target Windows environment.

Put uploads, staging, trash and converter temporary files on a dedicated volume with a hard filesystem quota, leaving operating-system space outside that quota. Application checks cannot reserve physical blocks against unrelated processes. Before enabling these changes, measure existing retained data and set finite budgets above legitimate usage; do not remove member data or alter account roles. Keep the existing resource/profile directory locations and migrate staging only after active uploads finish. Preview backfill and the live application must use the same environment and roots. On Linux verify `prlimit`, LibreOffice and FFmpeg are installed under an unprivileged service account.

Every material file response now requires the normal login cookie or a Bearer header and resolves only published, database-listed files. Metadata, notes, queue state and unknown paths return 404. Raw HTML, SVG, XML and other active formats download as attachments. HTML/SVG reports up to 2MiB remain viewable in the web application after sanitization inside an opaque sandbox: scripts, forms and embedded frames are removed; ordinary text, inline charts, styles and data images remain. HTML/SVG image references to database-listed raster files in the same material are fetched with a Bearer header by the parent and embedded as data URLs (50 images, 2MiB/image and 8MiB total; duplicates share a fetch). External images, cross-material references and CSS network background images are blocked. Selecting another file or leaving the page aborts pending image fetches. Larger active documents remain downloadable. Native clients fetch private media to temporary paths using a Bearer header and show document source as inert text; supported document downloads open in the device viewer. No reusable login JWT is placed in a material URL.
