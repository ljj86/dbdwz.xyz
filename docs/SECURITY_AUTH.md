# Authentication security update

The server creates the additive `auth_sessions` table from `server/db/auth-sessions.sql` during its existing database initialization. This needs the application's existing table-creation permission. The migration does not alter usernames, passwords, roles, or the meaning of `users.status` (online/offline). The `111` tester identity and existing role checks are preserved. Existing JWTs require one fresh login because they have no persistent session identifier.

Each new login creates a seven-day session. Every protected API, tutorial ticket/session, static tutorial request, and material or collaboration download checks that session and an HMAC of the current password hash. Logout revokes the current session, including copies of its bearer token, refreshed profile tokens, and its tutorial credentials. Password changes revoke all sessions for that user; the client clears its local credentials and opens the login page. A password reset through another trusted database workflow also invalidates previous tokens through the password binding. Profile changes retain the original session and expiry. Other users' sessions remain valid. Session rows survive application restarts; expired rows are removed on new login.

H5 previews and download links use the existing same-origin `dbdwz_token` HttpOnly cookie. Full login JWTs are no longer placed in material or collaboration URLs, and download routes ignore query credentials. API and native clients can continue sending `Authorization: Bearer ...`; a native downloader must send that header rather than append a token to its URL. The short tutorial ticket remains restricted to its existing two-minute tutorial exchange and inherits its parent session's revocation.

Login permits ten attempts per account and sixty per source address per fifteen minutes, with at most four simultaneous bcrypt comparisons. MySQL-resolved user IDs share an account budget across collation aliases. Username normalization runs only on bounded input; account and source map keys are fixed-size digests, the maps have fixed capacity, and no credentials are logged. Limits are local to the existing single Node process and reset when that process restarts. Additional workers would need a shared limiter before using the same deployment policy.

Login and current-password verification accept bounded historical bcrypt input up to 4096 UTF-8 bytes, preserving accounts created under the former character-count policy. Newly changed passwords require at least eight characters and no more than 72 UTF-8 bytes; new administrator passwords require at least twelve characters with the same byte limit. The browser displays that byte limit explicitly and applies the same UTF-8 count. Chinese characters usually occupy three bytes each, so 24 such characters fit; 25 do not. This avoids creating a new password that bcrypt silently truncates while retaining legacy login compatibility.

The login page now navigates as soon as authentication succeeds, removing its fixed 800 ms delay, and ignores a duplicate submission while a request is pending. The server still verifies bcrypt and persists the revocable session before responding. The non-authentication profile-file mirror runs afterward through one worker and at most 64 pending identities; pending jobs for the same identity are coalesced. Jobs keep only the user ID and login timestamp, read current account fields from MySQL under the same per-user lock as foreground profile writes, and preserve current drafts/preferences. Failed or overflowing mirror jobs do not retain an unbounded backlog or block a valid login. This metadata mirror is best effort; the existing startup/profile paths also synchronize profile data. Username, avatar and password mutations continue to await their own profile synchronization.

Keep the backend bound to loopback behind the local Nginx proxy. Express trusts only loopback proxies. The Nginx template overwrites `X-Forwarded-For` with `$remote_addr`, so a client cannot choose its login source bucket. A non-loopback direct client cannot supply a trusted forwarded address. When changing the proxy topology, update these two settings together.

Avatars accept decoded PNG, JPEG, GIF, and WebP raster images, up to the existing 8 MiB data URL limit and 16 megapixels. They are resized within 256 × 256 and re-encoded to WebP at quality 75 for the modern H5/Android WebView clients. GIF/WebP animation uses the first frame. If the encoded thumbnail exceeds 64 KiB, the converter retries at 192/128 pixels and lower quality, and never emits an image above that byte budget. SVG, malformed images, and mismatched declared MIME types are rejected. The public endpoint applies the same validation to old database avatars and sends `image/webp` with `X-Content-Type-Options: nosniff`; it does not overwrite existing database images during reads. Profile assets use the same validator with `.webp` names and remove unsafe historical avatar files during the existing profile sync. A shared two-conversion limit, eight-entry pending queue, in-flight image deduplication, and an 8 MiB result cache bound conversion work; a full queue returns 429 with `Retry-After: 1`.

Avatar URLs use a digest of the stored avatar plus a conversion-version prefix, so repeated login, `/me`, material lists and collaboration lists share the same URL while the image stays unchanged. A matching version receives a one-year immutable cache policy and an ETag; matching conditional requests return 304. Replaced images receive a different URL, and an old/missing version must revalidate. Login, user and collaboration DTOs contain the lightweight `avatarUrl` rather than an inline data URL; their SQL reads only presence and content-digest metadata. Login does not wait for initial thumbnail encoding. The profile editor previews the URL and omits `avatar` when no replacement was selected. The server preserves an omitted avatar, accepts a new raster data URL for replacement, and treats an explicit empty string as deletion.

EXIF orientation is applied before thumbnail resizing and metadata removal, preserving the displayed orientation of phone photos. The conversion-version prefix changes when this transformation changes, so cached images receive a fresh URL.

Avatar GET delivery also has two workers and at most 64 pending request contexts before reading data URLs from MySQL. This lets an ordinary member-list burst wait for thumbnails without holding dozens of large image buffers in the converter queue. A pending disconnect frees its place immediately; an active disconnect retains its worker until the current read/conversion finishes. Requests beyond this finite admission limit receive 429 with `Retry-After: 1`. The HTTP suite verifies that 50 distinct small avatars all load, queued requests perform no early database reads, and admission/cancellation remain bounded.

`PROFILE_ROOT` configures the shared root for account/profile assets, the per-user material trash and trash quota accounting. Without it, the existing project `个人资料` directory remains the default. Upload accounting imports this same resolved root rather than parsing a separate value.

## Local regression verification

Run `npm --prefix server ci` first. Set `SECURITY_TEST_TMP` to a prepared disposable output directory, then run `npm --prefix server run test:security-auth`. `SECURITY_TEST_MYSQLD` can select a local MySQL executable; the default is `/opt/homebrew/bin/mysqld`. The runner creates an empty private instance with `--no-defaults --skip-networking --mysqlx=OFF`, communicates only over its new private Unix socket, and terminates only its own process. Database files and synthetic profile/paper fixtures are deleted after the run; raw test and MySQL logs stay in the chosen output directory. It never loads `server/.env`, existing database configuration, or production files.

The suite runs actual HTTP requests against localhost Express and actual SQL against the empty MySQL fixture. It covers idempotent table creation; bearer/cookie and tutorial revocation; password changes and external resets; profile refresh and current role/name lookup; offline-status compatibility; legacy/malformed/expired/deleted-user tokens; raster-only HTTP and persistent avatars; bounded image work and cache eviction; cookie/header downloads without query credentials; collation-aware account/source budgets; malformed/oversized login input; bcrypt concurrency; historical multibyte-password compatibility; an unresolved profile-I/O gate while login already returns a usable session; bounded/coalesced queue behavior and failure recovery; profile-lock ordering and fresh database fields; immediate, single-submit client navigation; high-noise RGBA thumbnail dimensions/bytes; unchanged URL and ETag/304 behavior; lightweight authentication/collaboration DTOs; read-only legacy-image conversion; unchanged-avatar saves; replacement cache refresh; explicit deletion; and the editor's optional-avatar submission. Application-module reload is checked against the same persistent SQL state. Synthetic latency tests establish dependency ordering and are not production-login benchmarks. This test does not modify or deploy an online database.
